# Архитектура боевой системы RPS

Цель документа: превратить текущий черновик (`ChooseGesture` + 1v1 + HP) в расширяемое ядро, на котором можно провести **один бой уровня BG3** — без VFX и анимаций, только логика, данные и проверяемый симулятор.

BG3 здесь — не копия D&D 5e и не GAS «из коробки». Это эталон **тактической плотности**: несколько участников, экономика действий, дистанция, роли, статусы, реакции, ресурсы и ИИ, который делает осмысленный выбор. Разрешение столкновения остаётся **вашим RPS** (Strike / Guard / Feint), а не d20.

---

## 1. Что есть сейчас

Четыре файла в `Source/RPSbattle/Combat/`:

| Файл | Роль | Проблема |
|------|------|----------|
| `RPSTypes.h` | enum жестов и исходов, struct результата | Жесты зашиты в enum — новый жест = правка C++ и всех switch |
| `RPSResolver.cpp` | матрица 3×3 | Матрица в коде, множители магические числа, нет контекста (оружие, статус, дистанция) |
| `CombatComponent` | `MaxHP` / `CurrentHP` / `BaseDamage` | Нет атрибутов, ресурсов, статусов, фракции, инициативы |
| `CombatEncounter::ChooseGesture` | ввод + ИИ + резолв + урон + смена хода | Один метод = вся игра. Враг всегда `Guard`. Нет смерти, логов, событий, 1v1 |

Фактический пайплайн:

```
кнопка жеста → ChooseGesture()
  → враг всегда Guard
  → URPSResolver::Resolve(A, B)
  → ApplyDamage(BaseDamage * multiplier)
  → IsHeroTurn = !IsHeroTurn
```

Это валидный прототип ощущения «кнопки бьются». Это **не** архитектура. Дальше любой новый эффект (яд, AoE, второй враг, реакция) будет вписываться в `ChooseGesture` и сломает предыдущее.

Шаблонные `Variant_TwinStick` / `Variant_Strategy` к бою не подключены. Не тащить их в боевое ядро.

## 2. Архитектурное решение

### Выбранный стиль: **Data-driven content + фиксированное C++ ядро**

Не «всё в данных» и не «всё в классах».

- **Данные** описывают *что существует*: жесты, матрица, способности, эффекты, статусы, участники, сценарий боя.
- **C++ ядро** описывает *как это исполняется*: фазы хода, валидация, contest RPS, применение эффектов, истечение статусов, победа/поражение.
- **Акторы/виджеты** — тонкие адаптеры. Они шлют команды в ядро и слушают события. Не считают урон.

Это ближе к симулятору с DataAsset-ами, чем к Blueprint-спагетти или к полному Gameplay Ability System.

### Почему не GAS сейчас

Gameplay Ability System — правильный инструмент для сетевого action-RPG. Для этого проекта он дорогой и чужой:

- RPS — ваша идентичность. GAS заточен под Ability → Cue → Effect, а не под одновременный contest двух жестов.
- Проект на UE 5.8 уже с StateTree. StateTree закрывает ИИ и фазы боя дешевле, чем AbilityTasks.
- Цель — один проверяемый бой, а не инфраструктура плагина.
- GAS можно **навесить позже** как обёртку над тем же ядром (атрибуты/репликация). Если начать с GAS, RPS утонет в AbilitySpec.

Пересмотр GAS имеет смысл только после того, как ядро пройдёт один полноценный бой и понадобится репликация или предсказание.

### Почему не чистый ECS и не «всё в Blueprint»

- ECS (Mass) избыточен для 6–10 бойцов.
- Blueprint удобен для UI и контента, но матрица, статусы и порядок резолва должны быть детерминированными и тестируемыми без PIE.

### GameplayTags — да, сразу

Подключить модуль `GameplayTags`. Теги — дешёвый слой идентичности без новых enum:

- `Combat.Gesture.Strike`
- `Combat.Team.Player` / `Combat.Team.Enemy`
- `Combat.Status.Poisoned`
- `Combat.Ability.Melee`
- `Combat.Block.Actions`

Новый жест, статус или школа способности = тег + DataAsset, а не правка enum и всех switch.

## 3. Слои системы

```
┌─────────────────────────────────────────────────────────┐
│ Presentation (UMG, debug HUD, лог на экране)            │
│  только слушает FCombatEvent, не считает урон           │
├─────────────────────────────────────────────────────────┤
│ Runtime adapters                                        │
│  UCombatantComponent  — HP/ресурсы/ссылка на definition │
│  ACombatEncounter     — владеет сессией, ввод, таймеры  │
│  UCombatCommandSource — игрок / AI / скрипт             │
├─────────────────────────────────────────────────────────┤
│ Simulation kernel (без Actor*, без Tick)                │
│  FCombatSession  — участники, очередь, фаза, RNG seed   │
│  FCombatPipeline — TurnStart → Command → Resolve → End  │
│  FRPSMatrix      — таблица жестов                       │
│  FEffectExecutor — урон, хил, статус, ресурс, движение  │
├─────────────────────────────────────────────────────────┤
│ Content (UDataAsset / DataTable)                        │
│  Gesture, Matrix, Ability, Effect, Status, Combatant,   │
│  EncounterScenario                                      │
└─────────────────────────────────────────────────────────┘
```

Правило зависимости: **ядро не знает про акторов**. Адаптер переводит `AActor*` ↔ `FCombatantId`. Это даёт:

- автотесты боя без мира;
- возможность прогнать сценарий «головой» в лог;
- замену презентации (кнопки сейчас, камера позже) без переписывания правил.

## 4. Контракт ядра: команды, не кнопки

Сейчас кнопка *и есть* удар. В целевой модели кнопка шлёт **команду**, ядро решает, законна ли она.

```
FCombatCommand
  InstigatorId
  AbilityId          // не «жест», а способность
  TargetIds[]
  ChosenGesture      // опционально: если способность contested
```

Жест — параметр contest'а, не единственный вид действия. Иначе лечение, перемещение и бафф навсегда останутся костылями вокруг Strike/Guard/Feint.

Типы способностей:

| Contest | Когда | Пример |
|---------|--------|--------|
| `Contested` | цель может ответить жестом | удар мечом, выпад |
| `Save` | цель отвечает, но способность имеет «атакующий жест» из данных | яд, контроль |
| `None` | без RPS | шаг, лечение себя, смена стойки |

RPS остаётся сердцем боя, но не каждым действием.

## 5. Данные: что вынести из кода

### 5.1 Жест — DataAsset, не enum

`UGestureDefinition`: id/тег, отображаемое имя, опциональные теги (агрессивный / защитный / обманный).

Три текущих жеста остаются контентом по умолчанию. Четвёртый жест (если понадобится) добавляется ассетом и строкой в матрице, без правки resolver.

На старте можно оставить `ERPSGesture` как *legacy alias* и маппить его на теги, чтобы не ломать существующие кнопки. Новые системы читают только теги/ассеты.

### 5.2 Матрица RPS — DataAsset

`URPSMatrixAsset`: таблица `Attacker × Defender → FRPSOutcomeSpec`.

```
FRPSOutcomeSpec
  OutcomeTag              // Hit / Clash / Counter / (новые)
  DamageToDefenderMul
  DamageToAttackerMul
  GrantedTagsToWinner[]
  GrantedTagsToLoser[]
  ExtraEffectIds[]        // например Clash даёт «Ошеломление 1 ход»
```

Текущая логика переносится 1:1:

| Attacker \ Defender | Strike | Guard | Feint |
|---------------------|--------|-------|-------|
| Strike | Clash 0.5 | Counter (урон атакующему) | Hit 1.0 |
| Guard  | Hit 1.0 | Clash 0.5 | Counter |
| Feint  | Counter | Hit 1.0 | Clash 0.5 |

Resolver становится `Lookup(matrix, a, b)` + модификаторы из статусов. Никаких `if (Strike && Feint)`.

### 5.3 Способность

`UAbilityDefinition`:

- стоимость (очки действия, ресурс);
- дальность и фильтр цели (`Enemy`, `Ally`, `Self`, `Area`);
- тип contest;
- жест по умолчанию / допустимые жесты;
- список эффектов при Hit / Clash / Counter / Always;
- теги (оружие, заклинание, движение).

Новая атака = новый ассет, не новый C++ класс. C++ класс нужен только для *нового типа эффекта*, которого ещё нет в исполнителе.

### 5.4 Эффект — маленький примитив

Исполнитель понимает фиксированный набор:

1. `Damage` — величина, тип, масштабирование от атрибута
2. `Heal`
3. `ApplyStatus` / `RemoveStatus`
4. `ModifyResource` (мана, выносливость, ярость)
5. `Move` / `ForceMove` (шаг, толчок) — логика позиции, без анимации
6. `GrantAction` / `SpendAction`
7. `RevealOrLockGesture` — уникальная RPS-механика (см. §7)

Расширение: новый `EEffectOp` + ветка в `FEffectExecutor`. Это редкое событие. Контент-расширение идёт через комбинации существующих ops.

### 5.5 Статус

`UStatusDefinition`: длительность в ходах, стаки, хуки:

- `OnTurnStart` / `OnTurnEnd`
- `ModifyOutgoingRPS` / `ModifyIncomingRPS`
- `BlockTags` (нельзя действовать, нельзя двигаться)
- `OverrideGesture` (ошеломление всегда играет Guard)

Статусы — главный источник «BG3-ощущения» без анимаций. Яд, мокрый, маркировка, концентрация, разоружение читаются в логе и меняют следующий выбор.

### 5.6 Участник и сценарий боя

`UCombatantDefinition`: атрибуты, инициатива, набор способностей, стартовые статусы, профиль ИИ.

`UEncounterScenario`: список слотов (кто, команда, стартовая позиция), seed RNG, условие победы, матрица RPS для этого боя (можно шарить дефолтную).

Сценарий — это «уровень боя». Первый BG3-бой = один такой ассет, а не хардкод `TestHero` / `TestEnemy`.

## 6. Пайплайн хода

`ACombatEncounter` больше не резолвит. Он владеет `FCombatSession` и гоняет фазы:

```
EncounterStart
  → BuildParticipants(scenario)
  → RollInitiative
  → [TurnLoop]
       TurnStart          // тик статусов, реген, «пропуск если стан»
       WaitForCommand     // игрок или AI, с таймаутом только для AI
       ValidateCommand    // ход, дальность, стоимость, жив, не заблокирован
       CollectResponses   // если Contested/Save — жест защитника
       ResolveContest     // матрица + модификаторы статусов
       ApplyEffects       // по ветке Hit/Clash/Counter/Always
       CollectReactions   // один слот реакции, если есть
       TurnEnd            // снять истекшие статусы, проверить победу
  → EncounterEnd
```

Каждая фаза шлёт событие в лог и в UI. Смерть — не `return` посреди урона, а флаг участника + проверка в `TurnEnd` / после эффектов.

### Инициатива и экономика действий

Минимум для плотности BG3, без копирования PHB:

- **Инициатива** = атрибут + небольшой RNG (или фиксированный порядок из сценария для детерминированных тестов).
- **Очки действия (AP)** на ход: 2.
  - атака / заклинание = 1 AP
  - перемещение на 1 клетку/полосу = 1 AP (или отдельный Movement Point)
  - смена стойки = 1 AP
- **Реакция**: 1 на раунд. Тратится на ответный жест в чужой contest *если* способность/статус это разрешает (например Guard-stance даёт реакцию Counter).

Двух AP достаточно, чтобы был выбор «ударить дважды» vs «подойти и ударить» vs «бафф + удар». Три ресурса D&D (Action/Bonus/Reaction/Movement) можно не тащить в первый бой.

### Пространство без VFX

Полный навмеш не нужен. Нужна **логическая дистанция**:

- сетка или кольца: Melee / Close / Far;
- способность имеет `MinRange` / `MaxRange`;
- AoE — набор клеток/id относительно цели;
- прикрытие — тег клетки или флаг участника (`Cover.Half`), модификатор Clash-шанса или урона.

Для первого боя хватит сетки 8×8 или даже просто дистанции в метрах между акторами, округлённой до полос. Позиция — часть симуляции, меш — нет.

## 7. Как RPS масштабируется до «уровня BG3»

Не размножать жесты. Три жеста — читаемый язык. Глубина берётся из **модификаторов contest'а**.

| Приём BG3 | Аналог в этой системе |
|-----------|------------------------|
| Attack roll vs AC | Contested RPS |
| Saving throw | Save: способность несёт `AttackGesture`, цель отвечает |
| Advantage | `ForcedReveal` или запрет одного жеста у цели |
| Resistance | множитель типа урона на участнике |
| Concentration | статус, спасается через Save при получении удара |
| Opportunity attack | реакция при выходе из Melee |
| Spell slots | ресурс на `UCombatantDefinition` |
| Conditions (Stun, Poison, Wet) | `UStatusDefinition` + хуки в матрицу |
| Actions / Bonus / Move | 2 AP + реакция |
| Party 4 vs pack | `UEncounterScenario` на N участников |
| AI behaviour | StateTree / utility по профилю |

Уникальные RPS-крючки, которых нет в BG3 и которые стоит заложить сразу:

1. **Стойка** — последний сыгранный жест висит как статус до смены. Защитник без реакции отвечает стойкой, не новым выбором.
2. **Чтение** — способность Feint-школы накладывает `KnownStance` на цель: UI и ИИ видят её стойку.
3. **Ломка матрицы** — статус `OffBalance` превращает Clash в Hit против этой цели.
4. **Оружейный акцент** — меч даёт +множитель на Strike-Hit, кинжал — на Feint-Hit, щит — уменьшает урон на Guard-Clash. Это данные на способности/предмете, не новые жесты.

Так один и тот же Strike vs Guard читается по-разному у рыцаря, плута и отравленного гоблина.

## 8. ИИ

Враг больше никогда не играет `Guard` константой.

Профиль на `UCombatantDefinition`: веса жестов, предпочитаемые способности, трусость (хил/отход при HP < X).

Минимальный решатель (достаточно для первого боя):

1. Отфильтровать легальные команды (AP, дальность, живые цели).
2. Оценить каждую: ожидаемый урон × вес роли − риск смерти.
3. Для contested: предположить жест цели = её стойка, иначе взвешенный случай из профиля.
4. Выполнить лучшую команду.

StateTree уже подключён в `.uproject`. Использовать его как обёртку над этим решателем (состояния: Aggressive / Tactical / Flee), а не как место, где считается урон.

Игрок и ИИ реализуют один интерфейс `ICombatCommandSource`. Encounter не знает, кто на другом конце.

## 9. События и отладка вместо VFX

Ядро эмитит структурированный лог:

```
FCombatLogEntry
  Time / Round / ActingId
  Kind            // Command, Contest, Effect, Status, Death, Victory
  Text            // человекочитаемая строка
  Payload         // ids, числа, теги — для UI и тестов
```

Экран боя для верификации (не продакшен-арт):

- очередь инициативы;
- HP / AP / статусы каждого;
- кнопки способностей текущего бойца + 3 жеста;
- лента лога;
- сетка дистанции (debug draw).

Если лог позволяет восстановить бой без картинки — логика готова. Анимации подключатся к тем же событиям позже.

Детерминизм: `FCombatSession` хранит `FRandomStream` с seed из сценария. Один seed = одна replay-лента. Это критерий «отполировано».

## 10. Целевой бой №1 (acceptance)

Не «система в целом готова», а конкретный сценарий, который должен проходиться только на этом ядре.

**Сценарий: засада на мосту** (имя любое, состав фиксируем).

Сторона игрока (3 бойца, можно переключать между ними в их ходы):

1. **Страж** — высокий HP, способность «Удар щитом» (Strike-акцент, может наложить OffBalance), стойка Guard дешёвая.
2. **Плут** — средний HP, «Выпад» (Feint-акцент, бонус если цель OffBalance), «Чтение стойки».
3. **Травник** — слабый HP, «Лечение» (None), «Яд на клинок» (Save, накладывает Poisoned DoT).

Сторона ИИ (4 бойца):

1. Два **головореза** — мили, агрессивный профиль, чистый Strike.
2. Один **лучник** — Far, не идёт в мили, Save-выстрел.
3. Один **шаман** — бафф союзника + слабый contested удар, приоритет баффа.

Правила, которые обязаны сработать в этом бою:

- очередь из 7 участников, не 1v1;
- дистанция: лучник бьёт с Far, мили — нет;
- яд тикает на TurnStart и убивает, если HP низкий;
- OffBalance ломает Clash → Hit;
- реакция стража хотя бы один раз за бой (контратака при мили-ударе, если в стойке Guard);
- лечение проходит без RPS;
- ИИ не всегда Guard;
- смерть участника убирает его из очереди, бой кончается когда одна команда мертва;
- весь бой воспроизводится текстом в логе.

Если этот сценарий играется и проходит автотест с фиксированным seed — черновик стал механикой. Если нет — архитектура ещё не закрыта, даже если код «чище».

Вне скоупа этого боя: инвентарь, лут, диалоги, мультикласс, мир вне энкоунтера, анимации, звук, камера, сетевой мультиплеер.

## 11. Пошаговый план внедрения

Каждый шаг оставляет проект **запускаемым**. Не делать «большой взрыв». Кнопки трёх жестов живут до шага 6, просто начинают ходить в новую сессию.

### Шаг 0 — Развязать прототип

Файл: вынести расчёт из `ACombatEncounter::ChooseGesture`.

- `FCombatantId`, `FCombatantState` (HP, damage, team, alive).
- `FCombatSession` с двумя участниками.
- `URPSResolver` принимает жесты, возвращает результат; урон применяется в session, не в акторе.
- Encounter только: найти компоненты → прочитать состояние → вызвать session → записать HP обратно.
- Лог `UE_LOG` на каждый резолв.

**Готово когда:** старые кнопки работают как раньше, но `ChooseGesture` не содержит формулы урона.

### Шаг 1 — Матрица в данных + теги

- Модуль `GameplayTags`.
- `UGestureDefinition`, `URPSMatrixAsset`.
- Дефолтная матрица 3×3 = текущая таблица.
- Resolver читает ассет. Fallback на хардкод, пока ассет не назначен (чтобы не сломать PIE).

**Готово когда:** правка множителя Clash в ассете меняет бой без перекомпиляции.

### Шаг 2 — Сессия на N участников и ход как очередь

- Список участников, `Initiative`, `bAlive`.
- Фазы `TurnStart / WaitCommand / Resolve / TurnEnd`.
- Смерть при HP ≤ 0, победа по командам.
- `IsHeroTurn` удалить.

**Готово когда:** в PIE можно поставить 2 героя и 2 врагов, ходы идут по инициативе, мёртвый пропускается.

### Шаг 3 — Команда «способность», жест как аргумент

- `UAbilityDefinition` с одним эффектом Damage и contest Contested.
- Три текущие кнопки становятся **одной** способностью «Базовый обмен» + выбор жеста.
- ИИ: взвешенный случай жеста из профиля, не `Guard`.

**Готово когда:** бой 2v2 идёт способностями, лог пишет Ability + Gesture + Outcome.

### Шаг 4 — Эффекты и статусы

- Executor: Damage, Heal, ApplyStatus.
- Статусы: Poisoned (DoT на TurnStart), OffBalance (модификатор матрицы), Stunned (пропуск хода, жест = Guard).
- Длительность в ходах владельца статуса.

**Готово когда:** яд убивает без нового удара; OffBalance меняет исход Clash.

### Шаг 5 — Экономика и дистанция

- AP = 2, реакция = 1.
- Range band Melee/Close/Far из позиции актора или из логической клетки.
- ValidateCommand отвергает дальнюю мили-атаку.
- Перемещение как способность `None` за 1 AP.

**Готово когда:** лучник с Far не бьётся мили-ударом; за ход можно шаг + удар.

### Шаг 6 — Реакции и стойка

- Стойка = последний жест.
- Защитник без явного жеста отвечает стойкой.
- Реакция: заявленная способность (контратака стража) вставляется в `CollectReactions`.

**Готово когда:** в логе есть хотя бы одна Reaction-строка в тестовом сценарии.

### Шаг 7 — Сценарий боя как DataAsset + ИИ-источник команд

- `UEncounterScenario` собирает засада-на-мосту.
- `ICombatCommandSource` для игрока (UMG) и для ИИ (utility).
- Debug HUD: очередь, HP, AP, статусы, лог.

**Готово когда:** уровень спавнит бой из сценария, без `TestHero`/`TestEnemy` в коде.

### Шаг 8 — Детерминизм и автотест сценария

- Seed в сессии.
- Automation test: прогнать скриптовые команды (не PIE) до победы одной стороны; сравнить ленту лога с золотой.
- Второй тест: ИИ vs ИИ на том же сценарии не падает и заканчивается.

**Готово когда:** `UnrealEditor-Cmd ... CombatScenario.BridgeAmbush` зелёный. Это и есть «механика отполирована» без VFX.

### Шаг 9 — Контент боя №1, не движок

Только ассеты: 7 combatant definitions, ~8 способностей, 3 статуса, матрица, сценарий. Правки ядра — только баги, найденные прогоном.

**Готово когда:** человек проходит засаду, переключая трёх бойцов, и видит в логе все пункты §10.

## 13. Правила, которые нельзя нарушать

1. **Формулы не живут в акторах и виджетах.** UI шлёт `FCombatCommand`, читает `FCombatLogEntry`.
2. **Новый контент ≠ новый класс**, пока не нужен новый *примитив* эффекта.
3. **Не расширять enum жестов.** Только ассет + строка матрицы.
4. **Один RNG-поток сессии.** Никакого `FMath::Rand()` в резолве.
5. **Смерть и победа — фазы**, не побочный эффект `ApplyDamage`.
6. **Игрок и ИИ равны** перед пайплайном.
7. **Не подключать GAS, Mass, инвентарь, TwinStick** до закрытия боя №1.
8. **Каждый шаг оставляет три кнопки рабочими**, пока шаг 3 их не заменит способностью.

## 14. Порядок рисков

| Риск | Почему | Как снять |
|------|--------|-----------|
| Желание сразу сделать «как в BG3» | 5e-экран прячет RPS | Держать acceptance из §10 как потолок скоупа |
| Логика в Blueprint «на минутку» | Разъедется с тестами | Blueprint только UI и назначение DataAsset |
| Новый жест вместо статуса | Матрица раздувается, игрок теряет язык | Сначала OffBalance / ForcedReveal |
| Encounter-актор как God Object | Уже случилось в `ChooseGesture` | Session + Pipeline с шага 0 |
| ИИ в тех же if, что и урон | Нельзя тестировать по отдельности | `ICombatCommandSource` |

## 15. Итог

Текущий код — рабочий **contest loop**. Его нужно не выкинуть, а **сузить до lookup матрицы** и обложить сессией, данными и пайплайном.

Расширяемость даёт не «более умный resolver», а три вещи:

1. таблица RPS как данные;
2. способности/эффекты/статусы как данные;
3. фиксированный пайплайн команд, одинаковый для игрока и ИИ.

После шагов 0–8 один сценарий из семи бойцов с ядом, дистанцией, реакцией и логом — это и есть бой уровня BG3 на вашей системе. Всё остальное (анимации, камера, предметы мира) подписывается на уже существующие события и не имеет права менять правила.
